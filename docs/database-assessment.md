# Database Assessment

> 结论先说：**当前数据库设计对 LuvTALK 这个阶段是基本合理的，能支撑中小体量语言学习 App 的 MVP 到早期增长阶段；但“连接可靠性”和“数据库侧安全边界”还没有完全达到同体量成熟产品的稳态水平。**

## 1. 评估结论

| 维度 | 结论 | 说明 |
| --- | --- | --- |
| 数据模型合理性 | 良好 | 核心实体围绕 `User / Conversation / Review / Achievement / LearningGoal / TranslationRecord / ConversationReport` 展开，关系清晰，能覆盖当前业务闭环。 |
| 一致性与可维护性 | 良好 | Prisma schema 与 migration 链路已补齐，主表都有外键与核心索引，后续演进成本可控。 |
| 运行时可靠性 | 中等 | 当前 Supabase pooler + Prisma 运行时连接策略能跑，但对瞬时并发和连接抖动较敏感。 |
| 安全性 | 中等偏上 | 应用层鉴权链路已经统一到 Supabase token，但数据库层 RLS / policy 并未成为当前主防线。 |
| 同体量 App 适配度 | 可以满足 | 对“几千到几万 DAU、单租户、以 CRUD + 时序学习数据为主”的产品是够用的。 |
| 更大规模演进能力 | 需要补强 | 若进入更高并发、更多报表分析、更多实时协作场景，需要拆分读写压力和强化数据库治理。 |

## 2. 当前架构概览

### 2.1 数据存储角色

| 组件 | 当前职责 |
| --- | --- |
| Supabase Auth | 负责真实身份、邮箱 OTP、匿名用户升级 |
| Supabase PostgreSQL | 负责业务持久化 |
| Prisma | 作为主要 ORM / schema 管理 / migration 工具 |
| NestJS | 作为真正的业务权限边界与数据访问入口 |

### 2.2 当前认证与持久化路径

1. Web 端使用 Supabase Auth 获取 access token。
2. 请求到 NestJS 时，通过 `Authorization: Bearer <token>` 传入。
3. 后端调用 Supabase `/auth/v1/user` 校验 token。
4. 校验成功后，按 Supabase `user.id` upsert 到业务 `User` 表。
5. 后续 `Conversation`、`Favorite`、`ReviewFeedback`、`LearningGoal`、`UserAchievement`、`UserLevel` 等业务数据全部挂在这个 `userId` 上。

> 这个设计方向是合理的。  
> 它把“身份源”收口到了 Supabase，而不是前端自己再维护一套用户主键，避免了身份漂移。

## 3. 数据模型评估

### 3.1 设计合理的部分

| 模块 | 观察 | 评估 |
| --- | --- | --- |
| 用户域 | `User` 为业务主根，`email` 唯一，可兼容匿名升级 | 合理 |
| 会话域 | `Conversation` 绑定 `userId`，附带 `messages`、`title`、`status` | 对当前产品足够直接 |
| 收藏与翻译 | `Favorite`、`TranslationRecord` 都按用户维度归档 | 符合学习型产品常见建模 |
| 复习系统 | `ReviewQueueItem` + `ReviewFeedback` 分离“待复习状态”和“复习行为” | 有扩展性 |
| 成就系统 | `Achievement` / `UserAchievement` / `LevelDefinition` / `UserLevel` 采用“定义表 + 用户进度表” | 标准且可维护 |
| 学习目标 | `LearningGoal` 与 `LearningActivityDaily` 分离静态目标和日维度行为 | 合理 |
| 报告系统 | `ConversationReport` 独立存储结构化报告与 metrics JSON | 适合快速迭代 |

### 3.2 目前的建模短板

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| `Conversation.messages` 存在单个 JSON 字段中 | 读写简单，但后续难做精细查询、审计、搜索和归档 | 当消息量明显增长时拆分 `ConversationMessage` 表 |
| 多个表缺少更强的业务约束 | 应用层能兜住，但数据库层不能完全防脏数据 | 为关键字段补 `CHECK` 约束与更明确的非空规则 |
| `dateKey` 用字符串存储 | 可读但缺少原生日期语义 | 长期建议改成 `DATE`，或补衍生列 |
| JSON 字段较多 | 灵活，但分析查询成本会上升 | 热路径字段逐步结构化，冷路径继续保留 JSON |

## 4. 索引与查询设计评估

### 4.1 当前做得比较对的地方

Schema 里已经能看到一批贴近业务查询路径的索引，例如：

| 表 | 索引 | 价值 |
| --- | --- | --- |
| `Conversation` | `@@index([userId, updatedAt])` | 支持用户历史会话按时间倒序 |
| `Conversation` | `@@index([userId, targetLanguage, status])` | 支持按语言恢复会话 |
| `Favorite` | `@@index([userId, createdAt])` | 支持个人收藏列表 |
| `ReviewQueueItem` | `@@index([userId, nextReviewAt])` | 支持待复习卡片获取 |
| `ReviewFeedback` | `@@index([userId, createdAt])` | 支持复习行为统计 |
| `UserAchievement` | `@@unique([userId, achievementId])` | 防止重复写入同一成就 |
| `LearningActivityDaily` | `@@unique([userId, dateKey])` | 防止同日重复记录 |

这说明当前 schema 不是“先拍脑袋建表，再全表扫”，而是已经围绕主要用户路径做了基本索引设计。

### 4.2 还不够成熟的地方

| 风险点 | 说明 |
| --- | --- |
| 成就汇总仍依赖跨多表实时聚合 | 用户登录后立即同步成就，会把多次查询叠加到主连接上 |
| 大 JSON 会带来行变胖 | 如果 `Conversation.messages` 长期累积，历史列表查询会更重 |
| 缺少显式归档策略 | 长期运行后，报告、会话、复习反馈都会逐步放大主库体积 |

## 5. 可靠性评估

### 5.1 当前最大问题不在“表设计”，而在“连接设计”

从现有日志与代码看，数据库最主要的风险不是 schema 爆炸，而是：

| 风险 | 当前现象 |
| --- | --- |
| pooler 连接上限过紧 | 已出现 `MaxClientsInSessionMode`、`P1001`、`P1002`、`P2028` |
| Prisma 运行时连接过于保守 | 当前 `DATABASE_URL` 采用 transaction pooler `:6543?pgbouncer=true&connection_limit=1` |
| 登录后并发读放大 | `achievement`、`learning-goal`、`auth` 等链路会叠加访问数据库 |
| 降级机制存在，但意味着真实数据暂时不可用 | 用户会看到 fallback，而不是完整业务数据 |

> 这像是“仓库货架摆得还算整齐，但送货电梯一次只能上一个箱子”。  
> 表设计本身没太大问题，可是一到登录高峰，数据库连接这条竖井就容易堵。

### 5.2 对同体量 App 是否足够

如果你的目标是：

- 单项目单租户
- 几千到几万 DAU
- 大部分请求是用户自己的学习数据读写
- 报表分析需求不算重

那么当前设计是**可以用的**。

如果你的目标升级为：

- 高峰期大量同时在线
- 更复杂的 feed / 排行榜 / 推荐
- 更高频的实时协同
- 更长历史的行为分析

那么当前数据库层还不够，需要补：

1. 更稳定的连接策略
2. 更明确的读写隔离与缓存层
3. 行为聚合异步化
4. 大对象或历史数据归档

## 6. 安全性评估

### 6.1 当前安全上做得对的部分

| 点 | 说明 |
| --- | --- |
| 身份统一 | 后端最终认 Supabase 用户 id，而不是前端本地伪身份 |
| 服务端鉴权 | 关键业务接口不是裸连数据库，而是经 NestJS 应用层鉴权 |
| 不暴露数据库直写给前端 | 当前主要数据访问入口仍在后端 |
| 外键与级联删除 | 多数用户从表配置了 `onDelete: Cascade`，数据残留风险较低 |

### 6.2 当前还不够“成熟产品级”的地方

| 问题 | 风险 | 建议优先级 |
| --- | --- | --- |
| 没看到以 RLS 为核心的数据隔离策略 | 如果未来绕过后端直接开放 PostgREST/客户端直连，风险会立刻上升 | P0 |
| 应用层是主防线，数据库层约束偏弱 | 出现内部脚本、SQL Editor 手工写入时，更容易写脏数据 | P1 |
| `.env` 中存在真实连接串和密钥管理压力 | 对本地开发方便，但需要确保生产环境与仓库隔离 | P0 |
| 某些统计字段依赖代码计算而非数据库约束 | 容易出现“逻辑上正确，数据上不一致”的边界情况 | P1 |

> 当前是“后端守门型”安全模型。  
> 这对现阶段没问题，但如果以后想把更多 Supabase 能力直接开放给客户端，必须先把 RLS 补起来。

## 7. 是否满足同体量 App 设计

### 7.1 可以满足的场景

| 场景 | 结论 |
| --- | --- |
| 语言学习 App 的 MVP / Beta 阶段 | 可以 |
| 早期付费验证和功能闭环建设 | 可以 |
| 中等规模用户的个人数据读写 | 可以 |
| 单区域部署、单主库架构 | 可以 |

### 7.2 不足以放心支撑的场景

| 场景 | 原因 |
| --- | --- |
| 高峰并发明显上升 | 连接层比 schema 更先成为瓶颈 |
| 大量统计型页面同时打开 | 实时聚合会挤压 OLTP 主链路 |
| 后续开放更多客户端直连数据库能力 | 缺少数据库侧 RLS 体系 |
| 更复杂的数据治理要求 | 需要更细的审计、归档和生命周期管理 |

## 8. 建议的优先级路线

### 8.1 P0：尽快处理

| 项 | 建议 |
| --- | --- |
| 连接可靠性 | 重新校准 Supabase 运行时连接方案，减少对单一极小连接池的依赖 |
| 数据库安全边界 | 明确是否需要启用 RLS；如果未来要让前端直连任何业务表，先补 policy |
| 密钥治理 | 确保生产环境密钥不混入仓库，不在文档示例里泄露真实值 |

### 8.2 P1：近期优化

| 项 | 建议 |
| --- | --- |
| 成就/学习画像聚合 | 从“登录即实时全量同步”逐步转为异步聚合或事件驱动更新 |
| 消息存储 | 当 `Conversation.messages` 体积增长后拆表 |
| 数据约束 | 为关键业务字段补 `CHECK`、默认值和枚举约束 |
| 观测性 | 补充慢查询、连接池、重连次数、fallback 次数监控 |

### 8.3 P2：中期演进

| 项 | 建议 |
| --- | --- |
| 归档策略 | 历史会话、报告、复习行为做冷热分层 |
| 分析型数据 | 将复杂统计逐步下沉到汇总表或独立分析链路 |
| 多区域 / 更高可用 | 视用户增长情况考虑读副本、缓存层或任务队列分担 |

## 9. 最终判断

> 如果把数据库设计比作一栋楼：  
> 现在这栋楼的户型、承重墙和水电分区都不差，说明“建模方向”是对的；  
> 真正还不够稳的，是电梯调度和安保门禁。

因此，最终判断是：

- **数据库表结构与领域建模：合理**
- **对当前产品阶段：够用**
- **对同体量 App：基本达标**
- **对成熟产品标准：还缺两块关键补强**

这两块分别是：

1. **连接可靠性**
2. **数据库侧安全治理**

只要把这两块补上，这套设计完全可以继续往下演进，而不是推倒重来。
