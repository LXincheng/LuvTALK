| 维度       | 记录                                                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 复盘问题 1 | 用户反馈“回复变简单、教学信息不足、步骤不清晰”。                                                                                         |
| 根因分析   | Prompt 分层后，`text` 模式输出约束不够刚性；DS fallback 在纯文本返回时缺少结构化教学补偿。                                               |

| 根因分析   | optimistic 语音气泡未在服务端用户语音回显时及时收敛；会话刷新阶段存在误触发 pending 清理。                                               |
| 二次修复   | 回显到达即移除重复 optimistic 用户气泡，仅保留导师加载态；将状态清理锚点改为“真实 AI 回复到达”，减少过早消失。                           |
| 价值点     | 将体验优化从“表层样式调整”升级为“时序一致性 + 教学有效性”双闭环，形成可复用的排障与修复路径。                                            |

### 2026-03-10（线路切换双气泡与 Prompt 退化专项修复）

| 维度   | 记录                                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------- |
| 现象 A | 切换线路时出现两个语音气泡：一个为 optimistic `Voice message`，一个为服务端回显语音消息。                     |
| 根因 A | 之前仅在文本分支执行 optimistic 用户气泡去重，语音分支在部分回显时机下未及时收敛。                            |
| 修复 A | 统一“用户消息回显即去重”规则，不区分文本/语音；服务端用户计数增长即移除对应 optimistic 用户气泡。             |
| 现象 B | waiting 条在 API 返回后提前消失，但回复与语音稍后才出现。                                                     |
| 根因 B | 会话刷新 effect 依赖 `session` 对象整体，普通消息刷新也会触发 pending 清理，形成中间空窗。                    |
| 修复 B | 将清理逻辑收敛到 `session.id` 变化；`voice completed` 后执行短周期快照同步，直到真实 AI 回复到达再收敛。      |
| 现象 C | 用户反馈“回复变简单、步骤不清晰”。                                                                            |
| 根因 C | `text` 模式缺少强制分点约束；DS 非结构化输出时缺少教学化补偿。                                                |
| 修复 C | `text` 模式明确“两段输出”：目标语言回复 + 母语分点建议；服务端新增结构化补偿自动补齐 `Study Steps/学习建议`。 |
| 价值点 | 对话质量与教学目标重新对齐：既保证回复自然，也保证学习步骤可执行。                                            |

### 2026-03-18（修复：Prisma 瞬时断连后永久降级，改为自动重连）

| 维度   | 记录                                                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 问题点 | 当前运行时只要出现一次 `P1001/P1002`，`PrismaService.markDatabaseUnavailable()` 就会把数据库状态永久标记为不可用；之后即使网络恢复，进程也只会继续走降级，除非手动重启。 |
| 根因   | 现有 `PrismaService` 只有启动连接，没有后台重连机制，对 Supabase pooler 的瞬时抖动过于敏感。                                                                             |
| 修复点 | 为 `PrismaService` 增加后台自动重连：断连后按退避间隔调度重连，重连成功后恢复 `databaseReady=true`，不再要求人工重启服务才能恢复真实数据库读写。                         |
| 价值点 | 将“偶发网络抖动”从永久降级问题收敛为短时降级问题，减少成就、复习、会话等模块因瞬时断连长期停留在 fallback 状态。                                                         |
