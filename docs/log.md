## 2025-11：语音能力从 0 到 1

### 2025-11-16（SSE 与基础交互稳定）

| 维度     | 记录                                              |
| -------- | ------------------------------------------------- |
| 问题点   | 聊天反馈不够实时，发送后体感延迟明显。            |
| 修复点   | 增加 SSE 广播能力；前端引入乐观消息与事件流同步。 |
| 设计思路 | 先保证“消息先可见”，再异步补齐完整数据。          |
| 价值点   | 显著降低“发送后无反馈”的不确定感。                |

### 2025-11-19 ~ 2025-11-21（语音上传与转写闭环）

| 维度     | 记录                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 问题点   | 语音消息缺少统一入口和状态追踪，失败不可解释。                                              |
| 修复点   | 落地 `POST /conversation/:id/voice`，加入 MIME/大小校验与异步处理；转写后自动进入对话链路。 |
| 设计思路 | 将语音流程拆分为“接收 -> 转写 -> 回复”阶段化处理，并保持接口兼容。                          |
| 价值点   | 语音输入成为正式主链路能力，不再依赖手工流程。                                              |

### 2025-11-26（语音状态可观测）

| 维度     | 记录                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 问题点   | 用户无法知道语音当前处于哪一步，等待焦虑高。                                                                       |
| 修复点   | 引入 VoiceOperation 缓存与 `voice-status` 查询接口，状态覆盖 `received/transcribing/responding/completed/failed`。 |
| 设计思路 | 将“不可见异步任务”显式化为可轮询状态机。                                                                           |
| 价值点   | 大幅提升可解释性与故障定位效率。                                                                                   |

### 2026-03-10（当日问题反思与二次修复闭环）

| 维度       | 记录                                                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 复盘问题 1 | 用户反馈“回复变简单、教学信息不足、步骤不清晰”。                                                                                         |
| 根因分析   | Prompt 分层后，`text` 模式输出约束不够刚性；DS fallback 在纯文本返回时缺少结构化教学补偿。                                               |
| 二次修复   | 强化 `text` 模式为“目标语言回复 + 母语分点建议”；服务端新增文本模式结构化补偿逻辑，自动补齐 `Study Steps/学习建议` 的 1-2 条可执行步骤。 |
| 复盘问题 2 | 切换线路时出现双语音气泡，且 waiting 状态存在中间态闪烁。                                                                                |
| 根因分析   | optimistic 语音气泡未在服务端用户语音回显时及时收敛；会话刷新阶段存在误触发 pending 清理。                                               |
| 二次修复   | 回显到达即移除重复 optimistic 用户气泡，仅保留导师加载态；将状态清理锚点改为“真实 AI 回复到达”，减少过早消失。                           |
| 价值点     | 将体验优化从“表层样式调整”升级为“时序一致性 + 教学有效性”双闭环，形成可复用的排障与修复路径。                                            |

### 2026-03-10（线路切换双气泡与 Prompt 退化专项修复）

| 维度   | 记录                                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------- |
| 现象 A | 切换线路时出现两个语音气泡：一个为 optimistic `Voice message`，一个为服务端回显语音消息。                     |
| 根因 A | 之前仅在文本分支执行 optimistic 用户气泡去重，语音分支在部分回显时机下未及时收敛。                            |
| 修复 A | 统一“用户消息回显即去重”规则，不区分文本/语音；服务端用户计数增长即移除对应 optimistic 用户气泡。             |
| 现象 B | waiting 条在 API 返回后提前消失，但回复与语音稍后才出现。                                                     |
| 根因 B | 会话刷新 effect 依赖 `session` 对象整体，普通消息刷新也会触发 pending 清理，形成中间空窗。                    |
| 修复 B | 将清理逻辑收敛到 `session.id` 变化；`voice completed` 后执行短周期快照同步，直到真实 AI 回复到达再收敛。      |
| 现象 C | 用户反馈“回复变简单、步骤不清晰”。                                                                            |
| 根因 C | `text` 模式缺少强制分点约束；DS 非结构化输出时缺少教学化补偿。                                                |
| 修复 C | `text` 模式明确“两段输出”：目标语言回复 + 母语分点建议；服务端新增结构化补偿自动补齐 `Study Steps/学习建议`。 |
| 价值点 | 对话质量与教学目标重新对齐：既保证回复自然，也保证学习步骤可执行。                                            |

## 当前阶段总结（用于报告结论）

- 产品能力已从“可聊天”升级为“可教学、可复习、可追踪”的完整学习链路。
- 架构策略形成稳定范式：**主模型质量优先 + 多级兜底可用 + 前端状态机一致性控制**。
- 后续应优先推进三项：
  - 场景化教学模板继续细化（按餐厅/问路/商务等场景分治）。
  - 语音教学建议精细化（发音/节奏/语法建议个性化）。
  - 等待态与回复到达链路的端到端时延观测（为下一轮体验优化提供数据闭环）。
