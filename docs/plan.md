# LuvTALK 开发计划（v6.1）

> 更新日期：2026-03-29
> 当前阶段：场景链路已打通，进入 AI 服务系统级提速与稳定性治理阶段
> 当前主题：从“场景闭环可用”推进到“Chat / Immersive / Scenario 全链路更快、更稳、更一致”

## 1. 当前产品判断

| 维度           | 结论                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ |
| 已经做好的部分 | 自由对话、语音输入、沉浸模式、会话总结、复盘报告、收藏、复习、成长体系已具备基础能力 |
| 当前最大机会   | 把既有 AI 能力做成统一底座，让 `Chat / Immersive / Scenario` 都拥有更快首响、更稳反馈与更一致的教学质量 |
| 当前最大风险   | 各模块已共享会话和语音基础设施，但模型路由、超时、补全、翻译、TTS 仍分散演进，容易出现“某条链路突然很慢”或体验不一致 |
| 本轮产品重点   | 建立 AI 服务统一策略：首响优先、补强异步、分模块模型分层、全链路可观测、统一降级 |

> 接下来不再只盯某个单页体验，而是优先治理所有使用 AI 的核心模块，让系统整体时延、稳定性和产品感受进入同一标准。

## 2. 新主线目标

## 2.1 产品目标

| 目标     | 说明                                         |
| -------- | -------------------------------------------- |
| 强场景感 | 用户一进入就知道自己在练什么，不再是泛化聊天 |
| 强任务感 | 每个场景有明确目标和完成条件                 |
| 强沉浸感 | UI 简洁、角色明确、练习中尽量少噪音          |
| 强反馈感 | 结束后统一收到 AI 反馈和综合打分             |
| 强复练性 | 支持再练一次、换场景、保留历史               |

## 3.3 暂缓项

| 项目 | 原因 |
| --- | --- |
| 大规模场景商城 | 容易分散精力，先把核心链路和 AI 底座做稳 |
| 用户自定义场景生成器 | 需要更强内容治理，暂不进入首版 |
| 重型课程树 / 成就化包装 | 当前不是用户最短价值路径 |

## 4. 设计与技术原则

## 4.1 产品原则

| 原则             | 说明                                     |
| ---------------- | ---------------------------------------- |
| 独立入口         | 场景是独立训练链路，不是 Chat 的附属开关 |
| Walking Skeleton | 先打通主闭环，再逐步增强                 |
| 少解释，多体验   | 页面不堆满说明文字和教学口号             |
| 任务导向         | 每个场景都要有明确完成目标               |
| 结束反馈集中呈现 | 不把最终评价打散在聊天流里               |

## 4.2 工程原则

| 原则 | 说明 |
| --- | --- |
| 首响优先 | 实时对话、场景训练、退出沉浸后的反馈都优先返回“足够可用”的第一版结果，不等待重模型把所有细节一次性算完 |
| 补强异步 | 翻译、TTS、完整报告、扩展建议等可延后能力尽量异步补齐，不阻塞用户主动作 |
| 模块分层 | `chat / immersive / scenario / report / translation / tts` 分别定义适合自己的模型与超时，不共用一套粗暴默认值 |
| 强类型 | 所有场景定义、反馈结构、评分维度、模型返回结构必须类型化 |
| 配置优先 | 路由策略、模型优先级、超时窗口、回退开关可配置，不写死在业务组件 |
| 可观测 | 所有关键 AI 调用应可记录：耗时、模型、是否命中 fallback、是否本地兜底 |
| 可降级 | 上游慢或失败时，允许回退到本地启发式、缓存或轻量结果，避免整页卡死 |

## 5. 推荐实施顺序

| 阶段 | 目标 | 主要任务 |
| --- | --- | --- |
| Phase 1 | AI 链路盘点与统一门禁 | 统一 timeout / abort / fallback 封装；给核心接口补耗时日志；梳理各模块当前模型路由 |
| Phase 2 | 首响提速 | 将 `chat / scenario` 的文本主链切成低时延优先，长推理模型下沉到后台补强或仅用于重报告 |
| Phase 3 | 模块分层优化 | `immersive` 退出反馈、翻译、TTS、summary/report 全部按“轻结果先出、重结果后补”分层 |
| Phase 4 | 稳定性与学习闭环 | 接入收藏、复习、成长体系；补回归样例、性能基线和可观测面板 |

## 6. 下一阶段建议拆分

| 子任务 | 负责人视角 | 输出物 |
| --- | --- | --- |
| AI 路由治理 | 后端 / AI | 统一 `model-routing matrix`、超时策略、fallback 顺序 |
| 首响与补强拆分 | 后端 | `fast reply / async enrich` 基础能力，支持翻译、TTS、完整报告异步补齐 |
| Prompt 裁剪 | 后端 / AI | 分模块 prompt 预算、memory pack 收缩规则、history window 策略 |
| 可观测性 | 后端 / DevOps | AI 调用耗时日志、模型命中日志、fallback 统计 |
| 反馈体验收口 | 前端 | `ScenarioScoreModal`、Immersive 报告提示、Chat 等待态的一致视觉语言 |
| 回归评测 | 后端 / QA | 性能基线样例、prompt 质量样例、关键接口时延回归清单 |

## 7. 验收清单

### 体验验收

- 用户能在导航中明确看到“场景”入口。
- 用户进入后能快速选中一个真实高频场景。
- 场景开始前能理解自己和 tutor 分别扮演谁。
- 对话过程中如果卡住，能得到自然的引导。
- 练习结束后能收到有仪式感但不冗长的评分反馈。
- 深色和浅色模式都保持简洁高级，不脏不灰不花。
- 首屏能直接看到主要操作，不被超高头图区占满。
- 页面留白克制，信息密度更紧凑，但不显拥挤。
- 关键按钮位置稳定，用户不用反复寻找“开始”和“结束”。
- Chat、Scenario、Immersive 在等待 AI 时都不会长时间“无反馈”。
- 翻译、TTS、完整报告等补充能力即使稍后到达，也不会打断主操作链路。

### 工程验收

- 场景相关文案全部支持 i18n。
- React 组件内不硬编码大段场景内容。
- 类型系统能覆盖场景定义、session、hint、feedback。
- 新增场景功能不破坏现有自由对话和沉浸模式。
- Prompt 调整可纳入既有回归评测体系。
- 核心 AI 接口具备统一 timeout / abort / fallback 封装。
- 能从日志中区分模型慢、翻译慢、TTS 慢、报告慢分别发生在哪一段。
- 关键 AI 链路具备可复现的分段测速方法与基线。

## 9. 当前结论

> 现在最值得做的，已经不是再单点打磨某一个页面，而是把所有 AI 能力统一成一套“先快回、再补强、全链路可观测、失败可降级”的系统策略。只要 `Chat / Immersive / Scenario` 的首响、翻译、TTS、反馈都进入同一标准，产品体感会整体上一个台阶。
