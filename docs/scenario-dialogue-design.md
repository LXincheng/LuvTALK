# 场景对话功能设计与实现文档

> 更新日期：2026-03-28
> 适用阶段：场景对话功能设计评审 / 实施前对齐
> 设计基调：**苹果风格的克制高级感 + 更紧凑的信息密度 + 流畅清晰的任务动线**

## 1. 结论先说

当前 `Chat` 已经具备自由对话、语音输入、沉浸模式、总结卡与复盘能力，但它更像一个“开放式练习场”。

这次新增的 **场景对话（Scenario Practice）**，不是再做一个换皮聊天页，而是做一条新的训练主链路：

1. 用户先选一个明确场景。
2. AI 以该场景中的固定身份进入对话。
3. 用户卡住时可以获得引导，而不是被迫自己硬聊。
4. 练习结束后，系统统一输出 **AI 反馈 + 综合打分 + 下一步建议**。
5. 反馈以一个高级、简洁、动效克制但有仪式感的 `modal` 呈现，而不是塞进聊天流里稀释体验。

> 这条链路的价值，不是“比自由聊天多一个分类”，而是把产品从“能聊”推进到“能练、能卡点引导、能复盘、能提升”。

---

## 2. 产品定位与目标

| 维度                | 设计结论                                                                              |
| ------------------- | ------------------------------------------------------------------------------------- |
| 用户目标            | 针对真实生活或任务场景进行高密度练习，而不是泛泛聊天                                  |
| 产品目标            | 提升练习沉浸感、完成率、复盘价值和可复练性                                            |
| 与现有 Chat 的区别  | `Chat` 偏自由交流；`Scenario` 偏任务导向、场景约束、结束反馈                          |
| 与 Immersive 的关系 | `Immersive` 是交互模式；`Scenario` 是训练内容容器，后续可接文字 / 语音 / 沉浸三种练法 |
| MVP 范围            | 场景列表、场景进入、引导机制、结束评分 modal、历史记录、i18n、语音自然度约束          |

### 2.1 首批推荐场景

优先选“高频、低门槛、能快速体现价值”的场景，不要一上来铺太多冷门主题。

| 优先级 | 场景             | 训练目标                       |
| ------ | ---------------- | ------------------------------ |
| P0     | 酒店入住         | 身份确认、日期、房型、需求表达 |
| P0     | 感冒发烧去看病   | 描述症状、病程、药物、过敏史   |
| P0     | 餐厅点单         | 点菜、忌口、加减配料、结账     |
| P0     | 商店购物         | 问价格、试穿、尺寸、付款       |
| P0     | 问路与打车       | 描述地点、确认方向、时间距离   |
| P1     | 机场值机         | 护照、座位、托运、登机口       |
| P1     | 咖啡店下单       | 规格、冷热、甜度、打包         |
| P1     | 工作面试自我介绍 | 经历、优点、回答追问           |
| P1     | 商务寒暄         | 初见寒暄、交换信息、约后续     |
| P1     | 学校/课程咨询    | 询问课程、时间、费用、报名     |

## 3. 信息架构

## 3.1 导航结构

主导航新增一个一级入口：`场景 / Scenario`

| 入口                | 路径建议                                     | 说明                           |
| ------------------- | -------------------------------------------- | ------------------------------ |
| 场景首页            | `/scenarios`                                 | 场景选择、语言切换、推荐入口   |
| 场景详情 / 预开始页 | `/scenarios/:scenarioKey`                    | 显示角色、目标、难度、开始按钮 |
| 场景练习页          | `/scenarios/:scenarioKey/session/:sessionId` | 实际对话界面                   |

> 不建议把场景入口做成 Chat 页里的一个下拉选项。那样会让用户感知仍然是“同一个聊天页的一个模式”，弱化新功能价值。

## 3.2 用户流程

```text
导航进入场景
  -> 浏览预设场景
  -> 选择语言（普通话 / 粤语 / 英语）
  -> 查看场景简介与练习目标
  -> 开始练习
  -> 进入场景对话
  -> 需要时获取提示 / 引导
  -> 用户结束或系统判断完成
  -> 弹出评分反馈 modal
  -> 可选择再练一次 / 换场景 / 查看完整反馈
```

## 3.3 页面拆分建议

| 页面 / 区块              | 作用             | 设计重点                           |
| ------------------------ | ---------------- | ---------------------------------- |
| Scenario Hub             | 场景选择首页     | 高级简洁、强卡片识别、低干扰       |
| Scenario Hero Card       | 单个场景卡片     | 强化“任务感”，而不是课程感         |
| Scenario Prep Sheet      | 开始前准备面板   | 显示角色、目标、关键词、难度       |
| Scenario Session Page    | 实际练习页       | 保持沉浸，减少外围说明文案         |
| Hint Panel / Coach Sheet | 用户卡壳时的引导 | 只给必要提示，不抢答               |
| Scenario Score Modal     | 练后反馈弹窗     | 苹果风格、高级动效、信息极简但有效 |

## 4. 交互设计

## 4.1 场景首页（Scenario Hub）

### 设计方向

采用 `frontend-design` skill 推荐的 **refined minimal / luxury minimal** 方向，但要进一步收口成“紧凑而不拥挤”的苹果式页面：

- 留白克制，不空旷
- 轻玻璃质感与柔和边界
- 卡片内容精简但信息足够
- 不堆砌副标题和解释小字
- 首屏优先露出可操作内容，而不是大段氛围区
- 依赖层级、光影、动效和节奏感体现高级感

### 页面元素

| 区块     | 内容                                       |
| -------- | ------------------------------------------ |
| 顶部     | 页面标题 + 语言切换 + 推荐标签             |
| 主区域   | 场景卡片网格 / 横滑分组                    |
| 卡片信息 | 场景名、角色关系、练习目标、难度、预计时长 |
| 辅助入口 | 最近练过、继续上次、推荐给你               |

### 首页布局建议

| 区域     | 建议                                             |
| -------- | ------------------------------------------------ |
| 顶部高度 | 移动端 88-120px，桌面端 112-148px，避免超高 Hero |
| 首屏内容 | 首屏至少露出 2-4 张场景卡片                      |
| 卡片排列 | 移动端双列或紧凑横滑，桌面端 3-4 列              |
| 信息密度 | 每张卡仅保留标题、1 行 meta、1 个轻标签          |
| 操作路径 | 从进页面到点击开始练习，尽量不超过 2 次明显点击  |

### 卡片文案原则

- 不写长描述。
- 不写教学口号。
- 每张卡片最多保留 2 行有效信息。
- 场景名称和任务目标优先。
- 难度、时长、角色等信息尽量压缩在同一视觉带里。

示例：

| 场景     | 主标题   | 次级信息            |
| -------- | -------- | ------------------- |
| 酒店入住 | 酒店入住 | 前台登记 · 4-6 分钟 |
| 感冒看病 | 看病问诊 | 描述症状 · 5-7 分钟 |
| 餐厅点单 | 餐厅点单 | 点餐改单 · 3-5 分钟 |

## 4.2 场景开始前准备面板

进入具体场景后，先给用户一个短暂的“上场前”准备页。

| 模块     | 内容                         |
| -------- | ---------------------------- |
| 你的身份 | 例如“你是一位刚到酒店的旅客” |
| AI 身份  | 例如“AI 扮演酒店前台”        |
| 练习目标 | 本次要完成的 2-3 个任务      |
| 可选难度 | 基础 / 自然 / 挑战           |
| 开始按钮 | 明确进入练习                 |

> 这里的目标不是解释功能，而是帮助用户迅速进入角色。

### Prep 页收口原则

- 不做大段介绍文案。
- 不做居中空白大海报。
- 关键信息在一个主卡片内完成表达。
- 主按钮进入首屏可见区域，不让用户滚动寻找。

建议结构：

1. 场景名与角色关系
2. 2-3 个练习目标
3. 难度与语言
4. 立即开始按钮

## 4.3 场景对话页

场景对话页建议继续复用现有聊天基础设施，但视觉和交互要更“任务态”。

### 与现有 Chat 的核心差异

| 项目     | 自由 Chat           | 场景对话                     |
| -------- | ------------------- | ---------------------------- |
| 开场     | 任意自由开始        | AI 带着场景角色先开场        |
| 目标     | 宽泛                | 明确任务目标                 |
| 卡住处理 | 靠用户自己追问      | 提供提示、引导、重说建议     |
| 结束方式 | 自然结束            | 用户主动结束或完成目标后结束 |
| 反馈方式 | 会话总结 / 实时提示 | 结束后统一评分和点评         |

### 页内建议控件

| 控件                | 说明                                 |
| ------------------- | ------------------------------------ |
| `ScenarioHeader`    | 场景名、当前角色、进度态             |
| `GoalChips`         | 当前任务目标，可淡化显示，不抢主内容 |
| `HintButton`        | “给我一点提示”                       |
| `NudgeButton`       | “下一句我可以怎么说”                 |
| `EndPracticeButton` | 结束本轮练习                         |

### 对话页 UI 收口方向

| 项目     | 设计要求                                             |
| -------- | ---------------------------------------------------- |
| 顶栏     | 场景名、角色、退出入口尽量压缩在同一层               |
| 目标展示 | 用 `GoalChips` 或折叠式 goal strip，不做大块说明面板 |
| 对话区   | 减少无意义上下留白，让消息流更连续                   |
| 底部工具 | 提示、下一句建议、结束练习做成紧凑按钮组             |
| 输入区   | 延续现有风格，但边距更紧、结构更整洁                 |
| 页面节奏 | 一眼知道“当前在练什么、下一步做什么、怎么结束”       |

### 提示策略

引导必须像真人老师，不要像题库答案。

| 类型     | 触发方式                   | 输出风格                  |
| -------- | -------------------------- | ------------------------- |
| 轻提示   | 用户主动点提示             | 给 1 个方向，不给完整答案 |
| 表达提示 | 用户点“下一句我可以怎么说” | 给 1-2 句可直接说的话     |
| 任务提醒 | 用户偏题太久               | 轻量拉回当前目标          |
| 安抚提示 | 用户卡住 / 沉默过久        | 用自然口吻鼓励继续        |

## 5. 评分反馈 Modal 设计

这是本功能的视觉高潮，必须做得“简洁、克制、有仪式感”。

## 5.1 信息结构

`ScenarioScoreModal` 建议只放这些信息：

| 模块     | 内容                                            |
| -------- | ----------------------------------------------- |
| 顶部     | 综合分数                                        |
| 次级信息 | 一句极简评价                                    |
| 维度分   | 场景完成度 / 表达自然度 / 发音清晰度 / 应对能力 |
| 建议区   | 2-3 条短建议                                    |
| CTA      | 再练一次 / 继续下一个 / 查看完整反馈            |

### 极简评价示例

- “表达自然，关键任务完成得很好。”
- “能把意思说清，但追问时还可以更从容。”
- “核心信息完整，下一步重点练习更地道的说法。”

### Modal 版式收口

| 项目     | 建议                                                        |
| -------- | ----------------------------------------------------------- |
| 宽度     | 移动端接近系统 sheet 的满宽安全边距；桌面端控制在 420-520px |
| 高度     | 首屏完成主要信息阅读，避免超长滚动                          |
| 分数区   | 分数数字与一句评价作为唯一视觉核心                          |
| 维度分   | 紧凑四行或双列，不做夸张图表                                |
| CTA      | 主次按钮最多 2-3 个                                         |
| 文案密度 | 每条建议控制在一行到一行半                                  |

## 5.2 动效建议

### 整体原则

- 高级，不花。
- 动效服务于“完成感”和“评分浮现感”。
- 必须支持 `prefers-reduced-motion` 降级。

### 推荐动效分层

| 动效节点   | 建议效果                     |
| ---------- | ---------------------------- |
| 遮罩出现   | 轻微 blur + fade             |
| modal 入场 | scale + spring，上浮 12-18px |
| 分数数字   | 0 到最终分的缓动滚动         |
| 环形评分   | 微弱描边扫入 / 渐进填充      |
| 评价文字   | 逐行淡入                     |
| 按钮区     | 60-100ms 级联出现            |
| 退场       | 快速收束，不拖泥带水         |

### 视觉语言

- 白天模式：暖白、轻灰、淡金或冰蓝高光
- 夜间模式：深 graphite、玻璃黑、低饱和冷光
- 避免重紫色、重霓虹、重拟物

> 目标不是“炫动画”，而是做出一种像系统级结果面板的精致完成态。

### 动效节奏要求

- 首次入场顺滑，但总时长要短，避免拖慢反馈。
- 所有出现动画以 `180ms - 320ms` 为主。
- 分数动画可以略慢，但其他元素不要跟着拖。
- 页面切换和弹层展开优先“稳”和“干净”，不要弹跳过头。

## 6. 视觉系统建议

## 6.1 风格关键词

- 苹果风格
- 高级克制
- 玻璃感但不过度
- 强层级、弱噪音
- 紧凑但不拥挤
- 清晰而不是堆满装饰
- 白天 / 黑夜都成立

## 6.2 色彩建议

| Token                | Light            | Dark             | 用途         |
| -------------------- | ---------------- | ---------------- | ------------ |
| `--scenario-bg`      | 偏暖白 `#f6f7fb` | 深石墨 `#0f1115` | 页面底       |
| `--scenario-card`    | 半透白           | 半透深灰         | 卡片 / modal |
| `--scenario-accent`  | 冰蓝或银蓝       | 冷月白蓝         | 主强调       |
| `--scenario-success` | 柔和青绿         | 冷绿             | 高分态       |
| `--scenario-warning` | 柔和琥珀         | 低亮金棕         | 中等建议     |

## 6.3 字体与排版

保持现有系统不大改的前提下，建议通过以下方式拉开高级感：

- 大标题更紧凑
- 数字分数使用更强的字重与字距
- 卡片标题统一高度
- 减少说明文字密度
- 所有说明文案尽量控制在一行到两行
- 减少“标题下再跟长副标题”的习惯
- 页面模块之间优先用 12 / 16 / 20 的节奏，而不是过大的呼吸感

## 6.4 间距与密度建议

| 项目             | 建议值                              |
| ---------------- | ----------------------------------- |
| 页面主区垂直节奏 | 12 / 16 / 20 为主，不轻易超过 24    |
| 卡片内边距       | 移动端 14-16，桌面端 16-20          |
| 区块间距         | 同级区块控制在 16-20                |
| 按钮高度         | 主按钮 44-48，次级按钮 32-40        |
| 圆角             | 卡片 20-24，按钮 12-16，modal 26-32 |

## 6.5 苹果风格落地要点

不是简单使用毛玻璃，而是做到下面几点：

| 要点         | 说明                                 |
| ------------ | ------------------------------------ |
| 信息层级清楚 | 标题、操作、结果一眼能分出来         |
| 边界柔和     | 圆角、描边、阴影都轻，不厚重         |
| 内容先于装饰 | 背景效果不能抢文字和操作             |
| 流程顺手     | 用户很少需要停下来理解页面结构       |
| 结果面板高级 | modal 像系统原生结果页，不像营销弹窗 |

## 6.6 反模式

- 不要超高 Hero 导致首屏看不到可操作内容。
- 不要为了高级感把字做得太淡。
- 不要把每个信息块都做成独立大卡片，页面会碎。
- 不要过度使用渐变和彩色光晕。
- 不要出现大段居中文案，阅读会慢。
- 不要让按钮位置飘忽，尤其是“开始练习”和“结束练习”。

## 7. i18n 与组件解耦

这是本次设计的硬约束，不能把场景文案硬写进组件。

## 7.1 场景内容数据化

建议新增统一配置源，例如：

```ts
type ScenarioDefinition = {
  key: string;
  category: "travel" | "health" | "daily" | "work";
  icon: string;
  estimatedMinutes: number;
  difficulty: "basic" | "natural" | "challenge";
  supportedLanguages: LanguageCode[];
  i18nKey: {
    title: string;
    shortLabel: string;
    roleUser: string;
    roleTutor: string;
    goals: string[];
    starter: string;
  };
  promptProfile: {
    scene: string;
    successCriteria: string[];
    hintPolicy: string;
  };
};
```

## 7.2 文案拆分建议

| 类型                 | 放置位置                                                 |
| -------------------- | -------------------------------------------------------- |
| 通用 UI 文案         | `apps/web/src/locales/*.json`                            |
| 场景枚举配置         | `apps/web/src/features/scenario/scenario-definitions.ts` |
| Prompt 模板          | server 侧 prompt builder / scenario prompt config        |
| 多语言场景标题与目标 | locale keys，不写死在 React 组件里                       |

## 7.3 多语言支持范围

首版就要明确支持：

- 普通话
- 粤语
- 英语

需要区分两层语言：

| 维度                | 说明               |
| ------------------- | ------------------ |
| `targetLanguage`    | 用户正在练习的语言 |
| `interfaceLanguage` | UI 文案语言        |

场景提示、评分评价、按钮文案都要跟 `interfaceLanguage` 走；练习对话内容和 tutor 语言则跟 `targetLanguage` 走。

## 8. Prompt 设计建议

场景练习成功与否，核心不在 UI，而在 Prompt 是否足够具体、稳定、可控。

## 8.1 Prompt 总目标

让模型在场景模式下稳定扮演一个“自然、耐心、懂引导的角色型语言导师”，而不是普通聊天机器人。

## 8.2 Prompt 分层

建议沿用项目已有 `base / mode / level / safety` 思路，再新增 `scenario layer`：

| 层级       | 作用                                   |
| ---------- | -------------------------------------- |
| `base`     | 通用教学人格、输出边界、安全基线       |
| `mode`     | text / voice / immersive 差异          |
| `scenario` | 当前场景、角色身份、目标任务、结束条件 |
| `level`    | 难度控制                               |
| `feedback` | 练后评分与总结结构                     |

## 8.3 场景练习中的 Tutor Prompt 约束

### 核心约束

1. 始终待在角色里。
2. 对话自然，不像念题目。
3. 优先推动任务完成，而不是闲聊发散。
4. 当用户表达不完整时，先理解和承接，再做轻纠正。
5. 用户卡住时，允许提供提示，但不能直接接管整场对话。
6. 当场景目标完成时，可以自然收尾并引导结束。

### 示例 Prompt 结构

```text
You are playing a scenario-based language tutor.

Scenario:
- Key: hotel_checkin
- Your role: hotel receptionist
- Learner role: guest checking in
- Target language: Cantonese
- Interface language: Chinese
- Difficulty: natural

Goals:
- Confirm reservation name
- Confirm check-in date and room type
- Handle one extra request from the guest

Rules:
- Stay in character.
- Speak naturally like a real receptionist.
- Keep each reply concise in voice mode.
- If the learner struggles, give a subtle hint instead of a full answer.
- Prefer short conversational turns over long explanations.
- When enough goals are completed, wrap up the scenario naturally.
```

## 8.4 引导 Prompt

引导不是同一个 Prompt 分支直接硬回答，建议独立能力开关：

| 引导类型     | 输出要求               |
| ------------ | ---------------------- |
| 轻提示       | 给方向，不给完整句子   |
| 可直接说的话 | 给 1-2 句自然表达      |
| 纠错提示     | 先肯定，再给更自然版本 |
| 场景回拉     | 提醒当前任务节点       |

## 8.5 评分反馈 Prompt

练习结束后，单独触发一个 feedback 生成链路，返回结构化 JSON。

建议输出字段：

```ts
type ScenarioFeedbackPayload = {
  overallScore: number;
  summary: string;
  dimensions: {
    taskCompletion: number;
    naturalness: number;
    pronunciation: number | null;
    resilience: number;
  };
  strengths: string[];
  improvements: string[];
  nextActions: string[];
  CEFRHint?: string;
};
```

### 反馈约束

- 简洁
- 有用
- 不羞辱用户
- 不要过长
- 一句总评 + 2 到 3 条建议即可

## 9. 语音体验要求

用户特别强调 tutor 语音要自然流畅不卡顿，这里需要单独立规矩。

## 9.1 目标

让场景模式里的 tutor 更像真人服务人员 / 医生 / 店员 / 面试官，而不是“把文本念出来的 AI”。

## 9.2 约束建议

| 维度     | 约束                                     |
| -------- | ---------------------------------------- |
| 单轮长度 | 语音模式下尽量短句，避免大段播报         |
| 句式     | 更口语，更多真实停连                     |
| 节奏     | 适度停顿，不连珠炮                       |
| 文本生成 | 先为语音优化，再送 TTS                   |
| 场景人格 | 酒店前台、医生、店员、面试官要有不同语气 |

## 9.3 实施建议

1. 为 `voice` 场景模式单独设 Prompt 约束，控制句长与自然度。
2. 给 tutor voice style 增加“职业感”映射策略，而不只是通用柔和 / 自然 / 清亮。
3. 在服务端增加语音文本后处理规则，清理不适合口播的括号、列表、过长并列句。
4. 如果后续接入更适合对话的实时语音模型，优先让场景模式先吃到。

## 10. 数据与接口设计建议

## 10.1 前端数据结构

建议新增独立 `scenario` feature 目录，而不是继续把逻辑塞进 `ConversationPage`。

```text
apps/web/src/features/scenario/
  components/
  pages/
  data/
  hooks/
  types/
  utils/
```

建议类型：

```ts
type ScenarioKey =
  | "hotel_checkin"
  | "doctor_visit_fever"
  | "restaurant_ordering"
  | "shopping_in_store"
  | "asking_directions";

type ScenarioSessionStatus =
  | "ready"
  | "in_progress"
  | "completed"
  | "abandoned";
```

## 10.2 后端接口建议

| 接口                          | 作用                 |
| ----------------------------- | -------------------- |
| `GET /scenario/definitions`   | 获取场景列表与元数据 |
| `POST /scenario/session`      | 创建场景练习会话     |
| `POST /scenario/:id/message`  | 发送一轮消息         |
| `POST /scenario/:id/hint`     | 获取提示             |
| `POST /scenario/:id/complete` | 完成本轮并生成反馈   |
| `GET /scenario/history`       | 获取历史场景练习     |

### 兼容策略

首版可以复用现有 conversation session 基础设施，在 session 上增加：

- `scenarioKey`
- `scenarioVersion`
- `scenarioGoals`
- `scenarioState`
- `completionStatus`

这样能减少重复造轮子，同时保住已有会话、语音和总结能力。

## 12. 风险与注意事项

| 风险             | 说明                   | 对策                                |
| ---------------- | ---------------------- | ----------------------------------- |
| 过度复用 Chat 页 | 用户感知不到新功能价值 | 拆出独立入口、独立页面层级          |
| Prompt 不够硬    | AI 会跑题或失去角色感  | 增加 scenario-specific prompt layer |
| 评分太长太碎     | modal 失去高级感       | 控制为一句总评 + 少量建议           |
| 提示太强         | 用户变成抄答案         | 区分轻提示与直接可说表达            |
| i18n 混乱        | 场景文案写死后难维护   | 配置化 + locale key 拆分            |
| 语音口播僵硬     | 体验像读稿             | 单独 voice prompt 与口播清洗        |
